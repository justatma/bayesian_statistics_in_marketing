# Blind spec review: live view 01
Reviewed: spec/Live_View_Specification_v0.1.md against its §0, D41, D33, D34, spec v0.3 and the code it names.
Reviewer: Sonnet, fresh agent, no access to the author's reasoning. Date: 2026-11-07.

## 1. Where the spec does not implement the blueprint

1. §0 and D41 say a live feed monitored in a dashboard, with the inventory's four outcome classes kept distinct and the diagnostics gate preserving honesty. The page (§5 L3 C3, C4, C6) shows only delivery, platform-attributed, and the engine's evidence class. The spec does not say that commercially realized and causally incremental are deliberately absent from this page, nor that the page states their absence. Whether the page should say "not shown" for those two classes is an owner choice.

2. §0 says the foundation names a "daily (or intra-day) posterior refresh" with "the diagnostics gate preserving honesty at speed". L4 (§5) runs the engine for `ctr` only and the page (L3 C6) shows estimate, status and evidence class. It does not say the G3 diagnostics result of the run, or its absence for a conjugate fit, is shown. Spec v0.3 §12 C5 requires the report to carry it. Whether the live view needs it is undecided.

3. v0.3 §12 C1 (G7) says every rendered number comes from a bundle quantity with valid provenance. L3 C7 says "nothing on the page is computed from a quantity the store does not hold", which is a different rule. The delivery numbers, CTR, CPC and cost per conversion are computed in `view.py` from store rows and are not bundle quantities. The spec does not say that this is a deliberate exception to G7 for the internal page, and no decision row records it (D41 lists three v0.3 changes and this is not one of them).

4. D41 names three v0.3 changes: names and objective, `conversion_event`, account fields. The spec §3 also changes `purchase_type` into `conversion_type`, changes `Fetched`, moves `_meta_row` and the handler out of `tests/unit/p8` into `tests/fakes/meta_api.py`, and replaces the `meta_jovannah_7d` recording (§5 L1, §8). Preface line 4 says each change to v0.3 is a decision row. The recording replacement and the test-fake move have no row.

5. §0 says "a live feed", and D41 says "an hourly read of each client's ad account". The spec's poll (L2) and the page (L3) cover Meta only (`platform: Platform = "meta"`). The spec never says that Google Ads, LinkedIn and GA4 are out of scope for the live feed, or that `live poll --all` means all clients and not all platforms. The Jovannah config names Meta only (configs/jovannah.yaml), so this may be intended, but it is not stated.

6. §3.3 and D41 say the account read carries `amount_spent`, `spend_cap`, `account_status`. §3.3 also adds `name`. D41 does not list `name`. Minor; the row and the spec disagree.

## 2. Left undecided

1. §3.1: the insights fields to add are named (`account_name`, `campaign_name`, `adset_name`, `ad_name`, `objective`), but `objective` is not a field F2 lists on `act_<id>/insights`. The existing code comment says "F2 lists no objective or optimization-goal field" (src/bayesian_marketing/data_contract/connectors/meta.py:53-56). F2 marks the three entity names as INFERRED (spec/facts/F2_meta.md:76). `objective` on insights at `level=ad` may not exist at all; it is a campaign-level field read from a different endpoint. The spec says "a field the pack cannot verify is left out", but §5 L1 checks and C3/C4/C5 depend on `objective` being filled. What happens to the page when it is left out is not stated.

2. §3.1 and §5 L1: `PERF_TARGETS` in base.py already lists `entity_ids.account_name` etc. and `objective` (base.py:12-30), but the Meta `_record` in meta.py must map response keys to those names. The spec does not give the mapping from API key (`ad_name`) to target (`entity_ids.ad_name`), including `adset_name` to `entity_ids.ad_set_name`, which differ in spelling.

3. §3.3: `spend_cap` and `amount_spent` on `act_<id>` are strings in the account's minor currency unit (cents). F2 does not mention either field (grep of spec/facts/F2_meta.md for spend_cap, amount_spent, cents: no hits). §6 step 2 says "the cap line ($1,500)". The spec does not say whether `Fetched.account` holds the raw string or a converted value, or who divides by 100 and for which currencies. `account: dict[str, str]` fixes the type but not the unit. Unverified against the live API.

4. §3.3: the account call currently requests `timezone_name,currency` (meta.py:51, 215). Adding `name`, `account_status`, `spend_cap`, `amount_spent` changes the recorded account URL too. §3.1 mentions only the insights URL changing. Both recordings' account exchanges would stop matching. The spec's re-recording statement covers it only by implication.

5. §3.2 and L1 checks: `conversion_type(elements, wanted)` is specified for a config event, but the spec does not say whether `wanted` is matched against `actions` only or also `action_values`, nor what happens when the wanted type appears nowhere in the pull (the text says "value 0" and "the pull note says whether it was found"). It does not say whether such a pull still stores rows, and the page's behaviour for "event configured but never seen" is not stated.

6. §3.2: F2 lists `lead` and `offsite_conversion.fb_pixel_lead` as INFERRED and `onsite_conversion.lead_grouped` as UNKNOWN (F2_meta.md:90). Which string `configs/jovannah.yaml` will carry is left to F2 and the first client's account, and the config today has no `conversion_event` (configs/jovannah.yaml). Who edits the config, and what a lead client's `revenue_reported` is stored as (0 versus None), is open. D33 says leads are never valued, yet the spec stores `revenue_reported` as "value 0".

7. §4 contracts and §2 layout: `ClientConfig` has only `client_id, timezone, currency, accounts, economics_path` (core/records.py:83-90). There is no loader for `configs/<client>.yaml` in src (grep for ClientConfig outside connectors: none). The CLI subcommands take `--client <id>` but the spec does not say who loads the YAML, from which directory, or what `--all` enumerates (every file in `configs/`?).

8. §5 L4 C1: "priors from the client's config paths". `ClientConfig` has no priors path field and the spec adds only `conversion_event`. `CompareRequest.priors` is `dict[str, str]` of parameter path to approved prior id (core/records.py:145). Which prior paths a `ctr` run needs and where the ids come from is not stated. This also blocks the L4 acceptance fixture ("approved economics and priors fixture").

9. §5 L4 C1/C2: economics are located by `manifest.economics_id` under `manifest_dir/economics/<id>.json` (pipeline.py:279-283, 301), not by `economics_path`. The spec says "the client's economics file exists" and "economics ... from the client's config paths". How `economics_id` is derived from `economics_path`, and what `manifest_dir` is for a live run, is not decided.

10. §5 L4 C1: `DatasetManifest` needs `files: list[ManifestFile]`, `attribution_window`, `entity_map` (variant name to platform ids), `synthetic`, `envelope` (records.py:60-73). The spec does not say what the variant names are, what `entity_map` holds, the `ManifestFile` fields, or the `synthetic=False` setting. `CompareRequest` also needs `window` and `horizon`; "default horizon for CTR (impressions)" is named but the window is not (the whole 7-day lookback? the stored window?). `variants` for `ctr` is a list of ads, and the minimum count and what happens with one ad are not stated.

11. §5 L4 C1: the export CSV is "in the Meta export map's own column names". The map has no column for observed conversions and maps both "Purchases" and "Results" to `conversions_reported` (registries/channels.yaml:25-50). The CSV also needs a currency column or `{currency}` header and "Attribution setting". Which columns are written, and how a poll with `conversions_reported=None` is written, is not stated. Because each poll re-reads the same 7 days, how overlapping days across polls are handled in the run (only the newest poll's rows are used, per L2 C1) is implied but not stated for the CSV.

12. §5 L4 C2: "the gate's own reason text" for skipped. G9 is raised as `GateFailure` before reading (pipeline.py:949-951) and G8 later (pipeline.py:971-973), but a missing economics file, an unapproved file and a missing loss tolerance have different reason strings (pipeline.py:286-294). The spec says the skipped reason is one sentence "which approval is missing" (L3 C6) but a GateFailure carries a list of reasons. Join rule and which one shows are undecided. Also, the pipeline raises `GateFailure` for other gates (G1 on a stale channel model: `channel_model(platform, today)` in read.py:335). Whether G1 is a skip or a failure is not stated; as written it falls under "pipeline exception" and is `failed`.

13. §5 L4 C3 and L3 C6: the page reads `<data_dir>/runs/<run_id>.json`, but `snapshot_path` uses the process environment's `BAYES_DATA_DIR` through `data_dir()` (pipeline.py:185-189), not a parameter. `refresh(..., data_dir=)` and `render(..., data_dir=)` take a path. How the parameter reaches the pipeline (setting the env var, per call) is not stated, and the poll process and the view process must agree on it. The snapshot is a `RunSnapshot`, not the `Quantity` objects `_finding` and `_not_knowable` take (render.py:116, 148). How the page rebuilds `Quantity` objects from the snapshot is not stated. Also `_finding` and `_not_knowable` are private (underscore) helpers in `reporting`; the dependency rule in §2 lists only "reporting's phrasing loader".

14. §5 L3 C5: "the registry's event floors (about 17 for marginal, about 68 for estimable)" read through `registry_target`. That function returns a `PrecisionTarget` of half-widths (0.20, 0.40) and level (floors/estimability.py:61-68), not event counts. No function in `floors/` returns 17 or 68; a formula is implied (`(z/w)^2`). The builder must choose the formula, or a new function in `floors/`, which is outside L0's file list. "About" is not a testable number. "Conversions against the floors" is also not defined for a conversion count of None.

15. §5 L3 C5: the words `below floor`, `marginal`, `estimable` are said to come from "phrasing.yaml's status labels". phrasing.yaml has no such block (grep found none). The code's `_status_label` returns the raw status, or "not knowable yet" for `below_floor` (render.py:112-113). So the label text is not available as stated and the builder chooses it. If `phrasing.yaml` gains a key, that is a registry version change not listed in L0.

16. §5 L3 C3 and C4: CTR, CPC, "cost per conversion" are defined by name only. Not decided: numerator and denominator (link clicks over impressions, `inline_link_clicks`), the display for zero denominator, rounding (phrasing.yaml `rounding` has percent and money decimals; usage not stated), how multi-day windows are summed per ad, and how "today (account-local)" is computed given a window ending "today" and the account timezone. C7 says no percentage without its count, but how CTR "shows beside" counts is checked only as "beside", which cannot be asserted exactly.

17. §5 L3 C3: "last 7 days" and "whole window read" are identical when `lookback_days` is 7. The periods are presumably distinct only if lookback changes; not stated.

18. §5 L3 headings: the check asserts "the five section headings", but C1 to C8 list eight items, of which C1 header, C2 account line, C3, C4, C5, C6 are sections and C7 and C8 are not. The count is six or more depending on reading. Exact heading strings are not given.

19. §5 L3 checks and C7: the "banned phrase" test uses `negation_frames` and `generic_phrases` from phrasing.yaml. These include "more data", "more clicks" etc. (phrasing.yaml:32-45). The C5 sentence, "counts against floors", and the D33 sentence are not given verbatim, so whether they pass cannot be checked in advance. The D33 sentence and the stale/error banner texts are not fixed, so the acceptance tests would have to match on substrings the spec does not give.

20. §4 `Store` Protocol and §5 L2 C2: the store is append-only with triggers refusing UPDATE and DELETE on `polls` and `rows`, but `begin_poll` writes one row and `finish_poll(rec, rows)` "status may be error later; one row per poll". A second write of the same `poll_id` as an update is refused by the trigger. Either two rows per poll or a different mechanism is needed; the spec does not say which. `PollRecord.status` also has no "started" value. `latest_poll(ok_only=True)` resolving "by started_at" would then see two rows per poll. `RefreshRecord` and `refreshes` are not under the trigger, which is not said. A crash between begin and finish leaves a poll with no outcome; behaviour is not stated.

21. §4 `Store.open(path)` is written without `self` or `@staticmethod`/`classmethod`, and `Clock` and `Store` as `Protocol`s coexist with "`FakeStore`" in tests/fakes/live.py. The sqlite concurrency between the poll process (launchd interval) and the view process (KeepAlive) is not stated: journal mode, busy timeout, read-only connection for the view. `serve` uses `http.server`; whether it is threaded (`ThreadingHTTPServer`) is not stated, and one connection per thread rule for sqlite3 is not mentioned.

22. §4 `poll`: `PollRecord.window`, `pull_id`, `n_rows`, `n_quarantined`, `empty_account`, `timezone`, `currency`, `account` map from `PlatformPull`, but `PlatformPull` has no `account` dict (the new `Fetched.account` is not on `PlatformPull`; pull.py:170-188 builds it without one). How `Fetched.account` travels through `pull()` to `poll()` is not stated; `pull()` would need a new field on `PlatformPull` (a core record) which §3.3 does not list ("`PlatformPull.notes` is unchanged"). Also, `pull()` raises `ValueError` on bad window or missing account; C3 says "connector failure" becomes an error row, but the scope of exceptions caught (all `Exception`, `BaseException`?) is not fixed.

23. §5 L2 C1: `BAYES_RECORD_DIR` is set via environment, which is process-global; `pull()` uses `Transport.from_env()` (pull.py:108) and writes the recording only on success (commit_recording). The directory name uses `poll_id` which must be known before the pull; the id is `poll_<sha8>` of what input is not stated (v0.3 uses `inputs_hash`; two polls in the same second would collide if clock and inputs are identical). Setting an env var in a long-running process and restoring it is not described. When `record_root` is None (no `--record`), C4's ledger does not exist; the spec calls the recordings "the shadow ledger (protocol item 12)" but the default for `--record` and for launchd is not stated (the launchd poll plist is not said to pass `--record`).

24. §5 L2 C1: "account timezone from the previous poll, else the config's". "Last 7 account-local days ending today" does not say whether the window includes today (partial day) and what happens when Meta's today in the account zone differs from UTC date at the hour of the poll. Whether the 7 days are 7 inclusive of today or today plus 7 is not fixed.

25. §5 L2 C3: error text is "the exception's class and message, secrets redacted by the connector's own `redact_url`". `redact_url` takes a URL (http.py:126); an exception message is free text. How it applies to messages is not stated. C6's grep test lists "credential values" but the test needs the environment values; the fixture is not specified.

26. §5 L2 C5: "the CLI prints that it is early". Early is relative to which poll (last good or last any) is not said. With `RunAtLoad` the first poll after login and a manual poll both run early.

27. §5 L2 C4: `prune(record_root, clock, keep_days)` removes directories "older than" keep. Age is by directory mtime, by `poll_id` timestamp, or by the poll row's `started_at`; the directory name is `poll_<sha8>`, which holds no date. Not decided. Prune also runs from which entry point (its own CLI `live prune`; scheduled by what?). No launchd job for prune is listed in L0, so retention is not enforced unless run by hand.

28. §5 L0: the `Frozen` base, `Platform` and `Money` types are used in §4 contracts; `Money` inside `LiveRow` needs a storage encoding in SQLite (decimal text? integer minor units?) and `Money` currency per row; not stated. Row column set, primary keys, indexes, and the schema version are not given ("store schema" is an L0 deliverable with no content).

29. §5 L0: the acceptance tests are "written by an agent that will never build and frozen", but the L1 check says `data/recordings/meta_jovannah_7d/` is replaced by the re-recording (a live act by the integrator, with a real token) and "the P8 replay tests pass". The grep of tests shows `test_P8.py` and the unit tests reference `meta_empty` but not `meta_jovannah_7d` (tests/unit/p8/test_p8_connectors.py:234, tests/acceptance/test_P8.py:96). Which test replays `meta_jovannah_7d` and what it asserts, so the replacement stays valid, is not stated. Order dependency: L1 acceptance cannot pass until the re-recording exists; §3.1 says it happens before the frozen tests run but §6 step 1 (the first live poll) is listed as the smoke run after build. Who does the re-recording and in what order against test freezing is a cross-piece dependency stated only in a sentence.

30. §5 L0 and §1: L1 widens `core/records.py` and `channels.yaml` (labelled "skeleton"), while builders for L1 and L2 run together (§8). L2's tests depend on `Fetched.account` and `PollRecord` shapes; L3 depends on L2's store; L4 depends on L2 and on the pipeline. The dependency order of L3 on L1's names/objective output and L4 on L2 for rows is only implied by the pairing in §8 (L1 with L2, then L3 with L4).

31. §6: step 1 expects "rows for the five ads in the capped ad set". The Jovannah account was reported as empty at the last recording (commit b999d23 "empty account"), and the live account state is not something the spec can assert. This is the integrator's smoke check, but "five ads" and "$1,500" are facts not sourced in the spec or the registry. Unverified.

32. §7 item 5 and the owner decisions: the loss tolerance and CTR priors are named as owner-approved prerequisites, but L4 acceptance tests need fixtures for approved economics and priors. Whether the fixtures are synthetic (the G9 gate is bypassed when `manifest.synthetic`; pipeline.py:938-951) is not said. If the fixture manifest is `synthetic=True` the G8/G9 tests may not exercise the client path. This is a technical gap, not an owner choice.

33. §2 `registries/live.yaml`: the layout lists keys with `version, freshness_date`, but the §3.4 YAML shows only `version` and no `freshness_date`, and the account status map (C2 "a small map in `live.yaml`") appears in neither. The registry schema is "in L0" without a statement of whether `freshness_date` is checked (the channel registry uses a stale check that raises G1; read.py:335). Whether `live.yaml` staleness blocks anything is not stated. Key spelling for the status map is not given.

34. §5 L3 C8: `serve` logs "one line per request". Format is given (method, path, status, ms). The `Content-Type` and charset, the HTTP method handling for non-GET (405 versus 404), `HEAD`, and the behaviour for `/client/<unknown id>` (404 versus an empty page) are not decided. "Reads no query string" does not say whether a request with one is served with the string ignored or rejected. `render_index` content is not specified at all beyond its signature.

35. §5 L3: `<meta http-equiv="refresh">` of 300 seconds is given as a literal in the spec, not in `live.yaml`; hard-coded versus registry is a choice. The footer watermark is "the watermark for `internal` reports"; the key path (`watermark.internal`) is not named.

36. §5 L0 launchd: `StartInterval 3600` is hard-coded in the plist while `interval_seconds` is in the registry. Which governs is not stated, so a change of cadence ("a change of cadence in `registries/live.yaml`" is D41's revisit trigger) does not change the schedule. The interval on wake-from-sleep and a laptop being offline are not addressed; a missed hour produces a gap that the stale banner flags only after 2 hours. `install.sh` content, the python path and `.env`/keys loading for launchd (the token lives in a keys file per configs/jovannah.yaml) are not stated. The credential source for a launchd job is therefore undecided.

37. §2 and §8: the spec says "`live/` sits beside `atmaos/` ... imports ... `pipeline`" and "nothing imports `live/`", but cli.py (which L0 changes to add `live` subcommands) must import `live/`. The dependency rule needs an exception for `cli.py`; not stated. Also `[tool.setuptools.packages.find]` with `templates/live.html` needs package-data for the template; not stated.
