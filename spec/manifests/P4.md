## Facts assumed

VERIFIED

- w = (q95 − q05)/(2·q50); estimable ≤ rel_half_width, marginal ≤ caveat_rel_half_width, from `bounds/estimability/posterior_width` (spec §6.1, D10, D22 item 2, brief P4).
- `required` = n_events·(w/target)², labeled approximate in the reasons (spec §6.1, D22 item 5).
- Regime mismatches downgrade one level each, with a reason (spec §6.1).
- Decision: L = lowest expected loss among options; estimable ≤ tolerance, marginal ≤ marginal_multiplier × tolerance from `bounds/estimability/decision_loss` (spec §6.1, D9, contract assumption 21).
- No tolerance: below_floor with reason "no loss tolerance set" (D16, contract assumption 22).
- Signed quantities get basis "inherited" (spec §4.4, D10).
- Run record: one SQLite file under BAYES_DATA_DIR, triggers reject UPDATE and DELETE, `read` takes the class name and field-equality filters (spec §8.6, I7, contract assumption 23).
- Guarantees render from `guarantee_templates.yaml` only; only the four kinds; provisional entries refused (spec §8.5, I8, D15, contract assumption 24).
- `publish` raises GateFailure G2 on an unresolvable bound_ref; a published status is immutable; new data gets a new status with `supersedes` (spec §6.2, §13.1 G2, I5, contract assumption 25).
- Default store root `data/generated/` under the repo (brief `_common.md`).

INFERRED

- Regime-mismatch notices are matched by exact text against `phrasing.yaml` notices `lag_approx` ("lag-adjusted approximation") and `too_few_ads` ("funnel link not estimated: too few ads"), the two §6.1 mismatches that have a registry key. `platform_modeled` is not a regime downgrade (review fix 5).
- Signed quantities are `contribution`, `contribution_per_click`, `lift`. `quantity_feasibility` returns their existing feasibility relabeled "inherited", since it cannot see the inputs.
- When `n_events` is None, `available` is 0.0 and `required` is None, with the reason "event count unknown: available recorded as 0, required not projected" (core types `available` as float, so None is not possible; review fix 9).
- `required` is projected only when the width itself misses the target; a status limited only by a regime mismatch gets `required=None` with a reason (review fix 4).
- `quantity_feasibility` reads edge, caveat and level from the registry; a passed `PrecisionTarget` that differs raises ValueError (review fix 3). `registry_target()` is exported for callers.
- Decision `required` is None: the preposterior projection needs posteriors that a Comparison does not carry; a reason says so.
- With no tolerance, `target` is 0.0.
- `decision_feasibility` raises ValueError on an economics_id mismatch or a currency mismatch between loss and tolerance.
- Republishing a quantity id with the same status, basis and bound_ref is a no-op; any other change raises `StatusImmutableError`, whether better or worse.
- G2 also fails when `supersedes` names an id never published, when a quantity-precision status disagrees with the recomputed floor, when a quantity carries basis `decision_loss`, and when a superseding status improves without `data_pull_ids` strictly extending the superseded one's. Basis `inherited` is not recomputed.
- The status registry is a JSON-lines file (`status_registry.jsonl`), not SQLite, so the run record stays the only SQLite file under BAYES_DATA_DIR (test_P4 `_db` expects exactly one).
- Only locale "en" exists; any other raises.
- Precision levels 0.90 (q05/q95) and 0.95 (q025/q975) are supported; other levels raise.
- `read` returns objects in insertion order. RunRecord run_id and Recommendation recommendation_id are unique (append raises `DuplicateRecordError`); ApprovalRecord and OutcomeRecord may repeat per recommendation (P9 appends two outcomes for one recommendation).

## Open questions

1. §6.1 lists "attribution change in window" as a regime mismatch, but `phrasing.yaml` has no notice for it, so no downgrade fires for it. A registry phrase (notices.attribution_change) would let floors match it.
2. test_P5 asserts a platform-modeled CVR/ROAS is never estimable. With `platform_modeled` removed from the regime list (review fix 5), that holds only if the gamma_obs posterior is wide enough. If P5 fails there, the fix is a spec/registry decision adding platform-modeled conversions to the §6.1 mismatch list, not a floors change.
3. `Feasibility.available` is `float` in core, so it cannot be None when `n_events` is unknown (review item 9). Built: 0.0 with a reason. A core change to `available: float | None` would make it honest; core is outside P4.
4. Decision `required` (review item 10): neither preposterior simulation nor variance scaling is computable from `(Comparison, ClientEconomics)`. Variance scaling needs the current data volume behind the posteriors, and a Comparison carries only the horizon. Left None with a reason. Who owns the projection, and through which interface?
5. N2: the triggers stop UPDATE, DELETE and INSERT OR REPLACE, but anyone with file access can `DROP TABLE` (the table is then recreated empty on the next connect) or replace the SQLite file. That is tampering outside the API, which the triggers cannot prevent. Detecting it would need tamper evidence: for example a hash chain over rows, or a row-count and head-hash checkpoint written into each RunRecord. Is tamper evidence beyond the API required, and which piece owns it?
6. The status registry's I5 key includes the scope window, so it compares statuses only within one window. Should I5 also hold across windows for the same entity (e.g. latest window per ad and quantity)?
