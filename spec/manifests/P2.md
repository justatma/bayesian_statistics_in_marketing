## Facts assumed

VERIFIED

- Canonical header = first-listed header per field; `{currency}` replaced by the scenario currency (D20; `registries/channels.yaml` header comment; `tests/fakes/exports.py`).
- Manifest attribution window per platform defaults to the channel's `default_attribution_window`; orders gets `none` (`registries/channels.yaml`).
- Delivery: impressions on day d ~ Poisson(spend_d x 1000 / CPM); spend is an input (§5.2 C3, D8).
- Order value log-normal per ad, partially pooled (ad log median spread `ad_log_sd`) when not fixed (§5.2 C2).
- Lag curve family geometric (§14 registry defaults row "default lag curves"); conversions from day-d clicks observed at as_of only if they have happened (§5.6 C2).
- Google Ads conversions fractional under DDA (channels.yaml comment, F1 G7); `per_conversion_action` window not in the row (F1 G10), so the scenario states its click window.
- North Pier: A 40/2,000 and B 34/2,000 (day 2); A 8/400, B 18/340, spend $500 each, $80 price, $48 variable cost (§9.2, `tests/oracle/north_pier.py`).
- Delivery mix 800/200 -> 300/700 at 5% / 1%, 42 -> 22 (§9.2). Hold: $250 switching cost (§9.2, D22 item 14 format).
- `core.load_economics` looks in `<manifest_dir>/economics/<id>.json` first (D22 item 9).
- Synthetic flag `synthetic: true` on every manifest (D17, §9.1).

INFERRED

- North Pier truth rates are the Manuscript's observed rates (CTR A 2%, B 1.7% from day 2; CVR A 2%, B 18/340 from day 14; CPC $1.25 and $500/340). The Manuscript gives no "true" rates.
- North Pier day 2 conversions are drawn from that truth (the Manuscript gives none for day 2); day 2 spend $50 per ad (CPC x clicks).
- North Pier day 14 impressions are drawn as clicks + NegBin(clicks, true CTR) (Manuscript gives none for day 14).
- Fixed totals are split over days by multinomial (impressions, weighted by spend) and multivariate hypergeometric (clicks within impressions, conversions within clicks); fixed conversions have zero lag so all are observed.
- Geometric lag on whole days with p = 1 - 2^(-1/(median + 0.5)); click second uniform in the day; same-day order after the click.
- Platform conversions are reported on the click date and counted when elapsed time <= the click window in days; view-through is not simulated. Window code "<n>d_click..." parsed for n.
- Fractional credit per conversion ~ Beta(2, 2), reported to 2 decimals; reported revenue = value x credit.
- `loss_tolerance` values in every scenario's economics, the economics approver "scenario file (synthetic)" and approval date 2026-11-03: scenario choices so P11 can resolve approved economics; not from any source.
- All other scenario rates, CPMs, CPCs, spends, order-value medians and sigmas, day counts, hierarchy sds, many_accounts `ad_rho` -0.3: scenario choices.
- utm_source/utm_medium strings per platform (facebook/paid, google/cpc, linkedin/paid); utm_campaign unique per ad and `utm_map` keyed by it; utm_content = ad id; no click ids written.
- One export file per (platform, account), named `<platform>_<account id>.csv`; manifest `manifest.json`; no Google Ads preamble or Total row written; no ignored columns written.
- `true_quantities` per variant: ctr, cvr, cpc, cpm, order_value_mean, roas, contribution_per_click (price = fixed price or true AOV, minus variable cost); `true_best` objectives ctr, cvr, roas, contribution.

## Open questions

1. Economics: P2 writes `<out_dir>/economics/<econ_id>.json` with an approved ClientEconomics and a loss tolerance taken from the scenario file. Is approval-by-scenario acceptable for synthetic data, or does P11 want its own mechanism (test_P11 says P11 owns it)?
2. `switching_cost_hold`: `registries/channels.yaml` has `learning_phase_switching_cost: null` for meta, so reallocation computes the hold test at cost zero (§8.2 C1) and the true action (hold) is reachable only if a test sets the registry cost to `{amount: "250", currency: USD}` (recorded in GroundTruth.params). Should the scenario carry a registry override?
3. Scenario-level objectives that are not a variant (delivery-mix 42 -> 22, `true_action: hold`, realized latent correlation) live in `GroundTruth.params`, since `true_quantities` keys must be `<variant>.<quantity>` and `true_best` values must be variants.
4. `delivery_mix_shift` draws conversions, so realized blended orders per 1,000 clicks scatter around 42 and 22; only the truth is exact.
5. `fractional_conversions`: the orders file is still written (frozen test requires it) but carries no utm, so it cannot join (§5.1 C7). Confirm that is the intended reading of "only conversions_reported exists".
