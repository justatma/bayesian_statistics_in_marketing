- `lag_model(..., timezone, as_of)` and `lag_notices(lag)` (P7 follow-up in `spec/followups/open.md`).
- `load_economics(id, manifest_dir)` lookup order (D22 item 9); `allocate` resolves economics by id alone (`decision/allocation.py`).
- Metrics and objective rule (§11.1); compare's supported quantities and horizon units (`decision/compare.py` `SUPPORTED`).

- Sampler 4 x 1000 + 1000 warmup, target_accept 0.99 (D37, `registries/diagnostics.yaml`).

INFERRED

- One comparison runs on one ad platform; only the compared ads are fitted, so D11's "ads in a comparison" decides the route.
- `cpa`, `roas`, `contribution_per_click`, `contribution` compare `contribution_per_click` under the contribution objective; `ctr` and `cvr` compare themselves. The posterior entry shows the requested metric.
- `priors={}` resolves every registry default path through `prior_registry.resolve` (client, vertical, default). A requested id must equal the id its path resolves to; anything else (unknown, unapproved, superseded) fails G8. This uses only the public `resolve`, not the registry's private record reader.
- Observation date (`as_of` for maturity and lag censoring) is the window end, or the latest order date in the account timezone when the orders file runs past it. Without this, 2 of North Pier's 26 orders (ordered on Oct 15 UTC) were dropped and the 8 / 18 answer-key counts broke.
- An attribution window code with no click window or no registry median (Google `per_conversion_action`, LinkedIn `90d_click_90d_view`) and too little orders history: no lag adjustment (mature fraction 1), disclosed as "conversion lag not adjusted: no lag curve for attribution window ..." rather than borrowing a registry row.
- The window code in force is the latest row's (attribution window change scenario).
- Joint spec: gamma_obs CVR only when reported conversions are fractional and no observed count exists; log-normal value with orders, else compound gamma; hierarchy ad plus campaign and account when every ad has them; dynamics static.
- Signed `contribution_per_click` inherits the worst status of the same ad's `cvr` and `aov` (D10).
- A quantity whose summary is non-finite, or whose floor check overflows, is recorded as not estimable with a reason instead of reaching the report (G7 would block it).
- Recommend step is `allocate` (the socket names no incumbent for `reallocate`); its basis is set to the compared quantity ids.
- Run snapshot under `<BAYES_DATA_DIR>/runs/<run_id>.json` (write-once) carries what later socket calls need (evidence, narrative check, render).
- Replay scoring: per-day pulls (ids hash source pull and day) so each day strictly extends the last (I5); `not_knowable_correct` true only when the verdict came from a compared quantity with no events; regret uses share-weighted true contribution per click times the horizon.

## Open questions

1. `allocate` takes no economics and resolves the id without the manifest directory, so it reports "economics not found" for economics that sit beside the manifest. The pipeline sets `BAYES_CONFIG_DIR` to the manifest directory for that one call (`_economics_visible`); not thread-safe. Narrower fix (P9): `allocate(c, run_id, *, econ=None)`.
2. The 120-ad `many_accounts` joint fit fails G3 and falls back to the conjugate route, where 2 orders per ad give an order-value posterior with infinite variance (overflow warnings in `conjugate._draw`, `exp`). P3/P5/P6 to look at; P11 now reports those quantities as not estimable. The frozen smoke still takes about 4 minutes on that scenario.
3. `floors.quantity_feasibility` raises OverflowError on a huge width (`required = available * (w / edge) ** 2`); P4 could cap it.
4. Phrasing keys requested for P11 constants: `notices.lag_not_adjusted`, `notices.window_changed`, `reasons.client_needs_economics`, `requirements.economics`, `reasons.inherited_status`, `reasons.non_finite_spread`.
5. No lag curve exists for Google `per_conversion_action` or LinkedIn 90-day windows without 50 lagged orders; a registry row or the conversion action's click window from the connector would let the lag stage run (lag_heavy currently runs unadjusted, disclosed).
6. The report and recommendation evidence wording (P9 `EVIDENCE_BY_TARGET`, P10 comparisons) says "what the ad platform credited" even when conversions come from the orders file; P3 `derive` evidence also stays `platform_attributed` for orders-joined CVR on the conjugate route.
7. With fewer than 50 lagged orders the default 7-day curve applies even when the true lag is zero (North Pier), which adds the `lag_approx` regime downgrade: day-14 CVR for B is below floor through the pipeline, where §9.2 has it marginal on the oracle route.
8. `segments` supports only `{"ad": ...}`; campaign or account segments need the data read first.
